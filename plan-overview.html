Stage 0 done. Scroll performance half-solved. The app builds and runs against the real 1 121-mod setup. The scroll lag has been measured down to a single line of the mod row — four wrong theories eliminated with numbers rather than argument.

Base: upstream/master (WPF) Branches: master · fork/main · fix/* 2 commits on fix/publish-prebuild-quoting Windows now, Linux open 2026-09-23

Mod-name cost found and fixed — 220 → 21 µs per row

The name text in each row was the most expensive thing on screen for two reasons, both now fixed on perf/list-render. WPF re-did the work of shaping every name each time a row scrolled into view (twice). And every redraw paid a bookkeeping toll to the theme's shared text colour. A new text element shapes each name once and draws with a frozen copy of the colour. Measured with a scripted scroll, alternating old and new builds: the name costs 90% less, a thumb-drag frame drops from 33 to 25 ms of work, and frames that stutter past 33 ms are halved. The shared tooltip — the old prime suspect — was tested and ruled out.

New. A helper library is set up to package itself from a folder only a debug build creates, so on a clean checkout every release build fails. Nobody upstream noticed because their machines already had that folder. Build Debug once and it goes away.

2 · Zip export corruption
The file is opened without truncating, so exporting over a bigger zip leaves old bytes behind. Write errors are also silently swallowed.

3 · Archive import losses
The order file is read with one unchecked read, so big orders arrive truncated and get dropped silently. A failure flag also leaks between mods.
upstreamable
4 · Faster startup
Now measured: 9.3 s of the ~15 s is loading mods. Caching parsed metadata between launches is the obvious lever.

5 · Faster filtering + fuzzy search
Re-scoped twice. The delay is not the half-second wait — it is walking all 1 121 mods and toggling each one's visibility, which costs over a second even when nothing matches. You also want search to be fuzzy; that only becomes affordable once the per-keystroke cost is fixed, so speed comes first.

What to verify

Everything below is already built and sitting in bin\. Nothing here needs a rebuild. Delete the empty perfscroll file next to the exe if you ever see the app scroll and close itself — that is the test driver (it is removed after each run).

  • Drag the scrollbar thumb on the Active list. Open bin\Debug\BG3ModManager.exe and drag it top to bottom. It should feel clearly better than before, but not perfect yet — the other text columns still cost (next step).
  • Check the names look exactly as before. Same font, same sharpness, long names cut off at the column edge, selected rows' names in the selected colour.
  • Hover the empty part of a name cell. The mod's tooltip should still open there, not only over the letters.
  • Switch Light/Dark theme (Settings → Toggle Light/Dark Mode, or Ctrl+L) with the list visible. The names must change colour immediately along with everything else.
  • If you use a screen reader, check it still reads mod names in the list.
  • Say whether to do the other four columns next with the same fix.
  • Confirm the search feels as slow as it measures. Type a single letter into the search box and count. I measured up to ~3.8 s before it settles.
  • Check the release zip. BG3ModManager_Latest.zip in the repo root was produced by the proof run — open it and confirm it looks like a real release.
  • Decide on the game path. I pointed the test build at D:\Games\GOG\Baldurs Gate 3. Your real install of the manager is untouched, and your modsettings.lsx is byte-for-byte unchanged — I verified.
  • Say whether to push. Two commits sit on fix/publish-prebuild-quoting, unpushed.
