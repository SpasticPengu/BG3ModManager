# S9 — Stage 9 spec skeletons (update checker/downloader, native mods, dependency checks)

Status: **skeletons, not commitments.** Each feature below still needs its own spec session (implementation-plan §13).
This file gives each one a starting point: what exists, which external facts are confirmed, the open questions, and the decisions only the owner can make.
Order syncing is out of scope (covered with Stage 8 elsewhere).

Repo base: `master` == upstream `fc35358`. All work here is **FORK-ONLY** (`feat/*` on `fork/main`), except
the pre-existing bugs in §1.3, which are upstreamable `fix/*` candidates.

Evidence labels: **[src]** = read in source, with path:line. **[web✓]** = confirmed this session from a primary or official page.
**[web~]** = third-party or community source only. **[mem]** = from background knowledge, not re-checked.
**[inf]** = my inference. Reports folder (`scratchpad/reports/`) was **empty** when this was written and when I re-checked at the end,
so nothing here draws on SVC/BLD/AVA.

## 0. TL;DR

- Stage 9a means reviving **three half-built systems that don't connect**, plus **~12 latent bugs** (§1.3) that would surface the moment
  `"NexusMods": true` is flipped. Fix those first, as small upstreamable `fix/*` branches.
- **Ship a checker before a downloader.** The minimum viable step (§2.4) is user-initiated and Nexus-only, with roughly one API call per check
  thanks to `updated.json`. It puts a "newer file exists" badge in the existing Mod Updates panel and opens the mod page. No files are written.
- **A Nexus downloader for non-premium users needs nxm:// handling** [web✓]. That means a protocol handler, single-instance IPC
  (master has none [src]), and a policy for coexisting with Vortex/MO2. This is the biggest design chunk.
- **A public fork using personal API keys is grey under the Nexus AUP** [web✓]. Decide whether to register the app (D1).
- **Store keys with DPAPI (`ProtectedData`, CurrentUser) behind a small `ISecretStore`** so Linux stays open (§2.2).
- **Native mods carry the highest blast radius.** They touch `bin/` next to the Script Extender's `DWrite.dll`, and NML's proxy
  is `bink2w64.dll` [web~]. Treat them as *detect and report first*, then *manage `bin/NativeMods`*, and never touch `DWrite.dll`.
- **Dependency checks need no network for their first and best step.** `meta.lsx` already carries dependency `Version64`, which is parsed
  but never compared [src]. A local "outdated dependency" warning is cheap and could even go upstream.

## 2. Shared foundations (needed by 9a and 9c; specify once)

### 2.1 Mod identity: mapping an installed mod to a remote page

The checker is only as good as this mapping. Candidate sources, in roughly descending reliability:

1. **User-entered Nexus mod id or URL** per mod. This needs a small UI (§2.6) plus persistence, and the Nexus cache already persists `mod_id` per UUID (`NexusModsModData.cs:44`, `NexusModsCacheHandler.cs:41-44`).
2. **Archive filename at import.** It exists today, but fix B6 and parse only modId plus upload timestamp.
3. **`PublishHandle` → mod.io mod id.** Upstream avalonia assumes this (`wt-avalonia/src/Services/Services/External/ModioService.cs:54,78,88`) [src]. **Not confirmed** by any doc I found [web~ only shows `PublishHandle=0` examples]. Needs an empirical check with one mod.io-installed mod (open question Q-M1).
4. **Nexus `md5_search`** (`/v1/games/{game}/mods/md5_search/{md5}.json`, route present in upstream's vendored NexusModsNET `Internals/Routes.cs:111` [src]). It hashes the **downloaded archive**, not the extracted pak [inf], so it only helps if the manager keeps archives (it doesn't today) or the user points at one.
5. Fuzzy name search: **excluded**. Too many false positives for something that later downloads files [inf].

Open: should the mapping live in the existing per-source caches (`Data/nexusmodsdata.json`) or in one new `Data/modsources.json` keyed by UUID? The latter suits Stage 8's export format and order syncing better [inf].

### 2.2 Secret storage (Nexus key, mod.io key or OAuth token)

Today: plaintext in `Data/settings.json`. Both release paths delete `Data/` (CLAUDE.md §7), which protects only release zips, not users.

### 2.3 Network error surfacing

New code must not use `WebHelper.DownloadFileAsStreamAsync` as written (`WebHelper.cs:18-30`). Use `HttpResponseMessage` and status
codes, map 401/403/429 to distinct states, and surface them via `ShowAlert` (risk R8). A "no updates" result must be distinguishable from "check failed".

### 2.4 Minimum viable update checker (MVP, ship first, no downloads)

Scope: **Nexus only. User-initiated** (a "Check for mod updates" button or menu item; the AUP forbids using keys "without the action being initiated
by the user" [web✓], see Q-N3). Results feed the Mod Updates panel.

Algorithm (Nexus; endpoints confirmed by upstream's vendored client routes [src] and third-party docs [web~]):

1. Mods with a mapped Nexus id: `N`.
2. **1 call:** `GET /v1/games/baldursgate3/mods/updated.json?period=1m` (or `1w`/`1d` chosen from the last-check time). Its documented server-side cache is 5 min (`Routes.cs:126` comment [src]). Intersect with `N`, giving candidates `C`.
3. For each mod in `C` (and every mod never checked): `GET .../mods/{id}/files.json`, then pick the latest MAIN or primary file, keeping `file_id`, `version`, `uploaded_timestamp`, plus `file_updates` chains [web~].
4. Decide "update available", in confidence order:
   - a. A recorded installed `file_id` (once B6 is fixed and file ids are captured at install time) != latest primary `file_id`, or the `file_updates` chain leads from it. **Strongest.**
   - b. The remote file's `uploaded_timestamp` > the filename-parsed upload timestamp, or the pak's install time.
   - c. **Version64 vs remote version string.** Parse the remote string to `DivinityModVersion2` (`Major<<55 | Minor<<47 | Revision<<31 | Build`, `DivinityModVersion2.cs:29-32`) only when it matches `^\d+(\.\d+){0,3}$`, then compare `>`. Show this as a *hint*, because Nexus version strings are author free text and often don't match `meta.lsx` [inf].
5. Budget: about `1 + |C|` calls per check, against 20,000/day [web✓]. Show remaining hourly/daily quota using the existing status-bar hook (`OnNexusModsRateLimitsUpdated`, `:4873`), finally wired.

Output per row: local name/version, remote version, remote upload date, confidence (a/b/c), "Open page" (fix B7). **No file writes in the MVP.**

mod.io MVP (second): one search call with `id-in` over mapped ids (upstream does exactly this, `ModioService.cs:78-83` [src]), then compare
`modfile.version` / `date_added` the same way. It is blocked on Q-M1/Q-M2.

### 2.5 Download and install safety (only once the downloader is approved)

Requirements for the spec, regardless of source:

- **Staging:** download to `Data/Downloads/<source>/<id>/<file>.part`, then rename to the final name when complete. Never write straight into `Mods/`. Upstream writes directly to the final path (`DownloadManagerService.cs:87`) [src].
- **Verify:** mod.io gives `filehash.md5`, `virus_status`, `virus_positive` (`modio.net/Modio/Models/Response/File.cs:39,45,105`) [src]. Reject on mismatch or `virus_positive != 0`. Nexus `files.json` exposes a per-file md5 [mem, unconfirmed]; Q-N6. Neither upstream's `ModioService` nor `modio.net`'s `Client.Download` checks the hash (`Client.Download.cs:105-136`) [src].
- **Quarantine:** extract to `Data/Downloads/.../extracted/`, then run the existing import validation (pak → meta.lsx → UUID). Reject archives containing `.dll/.exe/.asi` unless the target is the native-mods flow (§4). Watch for zip-slip on extraction [inf].
- **Never overwrite a pak in use:** refuse while `bg3.exe`/`bg3_dx11.exe` is running (revive the commented check at `MainWindowViewModel.cs:5424-5425`). Also try opening the target with `FileShare.None` before replacing.
- **Atomic install + rollback:** move the old pak to `Mods_Old_ModManager/<UUID>/<timestamp>/` (the folder B8 creates but never uses), then `File.Move` the new pak into place, update the mod list, and offer "Revert" from the backup. Same volume means the move is atomic [inf]. Cap the number of backups.
- **Same-UUID guard:** if the new pak's `meta.lsx` UUID differs from the mod it is meant to replace, stop and ask.
- **No silent load-order change:** an update keeps the mod's position in the active order. A new dependency is added as *inactive*, with a prompt.
- **Queue:** at most 2 concurrent downloads (upstream's default, `DownloadManagerService.cs:24`), cancellable, one shared `HttpClient`. `modio.net` creates `new HttpClient()` per download (`Client.Download.cs:107,126`) [src]. Avoid that.

### 2.6 UI placement: reuse the dead Mod Updates view

- Keep the host slot (`MainViewControl.xaml:504`), the toggle button, the count badge, and `ToggleUpdatesViewCommand`. They already work, they just have no data.
- **Replace `DivinityModUpdateData`'s model** (a local pak vs an updated pak) with a source-agnostic row: `{Mod, Source, RemoteVersion, RemoteDate, Confidence, PageUrl, DownloadState}`. Keep the "new / updated" two-section layout, so `IsNewMod` maps to "dependency not installed" for 9c.
- Retire `CopySelectedMods_Run` (`ModUpdatesViewData.cs:87-121`) in favour of §2.5's install path. Don't fix its copy loop.
- Settings: an "Integrations" tab with a Nexus key field (masked; "Get key" link; "Test" shows the user, premium status, and quotas), a mod.io key field, and an nxm handler toggle (§3.2). Remove `HideFromUI` from the key, or better, move the key out of `DivinityModManagerSettings` into `ISecretStore`.
- Per-mod context menu: "Set Nexus mod id…", "Open on Nexus/mod.io", "Check for update".
- Stage 7 (UI refresh) will restyle this. Build it as plain VM plus minimal XAML [inf].

nxm:// protocol handler on Windows [mem unless noted]:
- Register per user under `HKCU\Software\Classes\nxm` (`(Default)="URL:NXM Protocol"`, `URL Protocol=""`, `shell\open\command="\"<exe>\" \"%1\""`). No admin needed.
  Upstream writes through `Registry.ClassesRoot` (`wt-avalonia/src/Services/Services/Reg/WindowsRegistryHelper.cs:111-136`) [src]. Creating a *new* key via HKCR lands in HKLM and needs elevation [mem]. Use HKCU explicitly.
- **Coexistence:** Vortex and MO2 also claim `nxm` [mem], and MO2 ships an `nxmhandler` that dispatches by game [mem]. Upstream overwrites any existing handler without asking (`WindowsRegistryHelper.cs:127-131`) [src].
  Spec must: show the current owner, ask before taking over, remember the previous command, and offer "restore previous handler".
  Ideal: handle only `nxm://baldursgate3/...` and forward other games to the previous handler [inf] (Q-N4).
- **Single instance:** a second exe launched with the nxm URL must hand it to the running instance. **Master has no mutex or IPC** (`App.xaml.cs:59-78` ignores `e.Args`) [src]. Upstream uses a named pipe (`BackgroundCommandService.cs:2,13,30`) [src]. A named pipe is portable to Linux [inf].
- Linux later: `.desktop` file with `MimeType=x-scheme-handler/nxm;` + `xdg-mime default` [mem].

- **Don't download mod.io mods yourself at first.** The game already manages them. A manager that also overwrites those paks risks fighting the in-game manager.

## 4. 9b — Native mod management

### 4.1 Realities

| Fact | Status | Source |
|---|---|---|
| "Native Mod Loader" (Nexus BG3 mod 944) installs a proxy `bink2w64.dll` in `bin/` and renames the original to `bink2w64_original.dll`; native DLL mods go in `bin/NativeMods/` | **web~** (mod page and comments) | nexusmods.com/baldursgate3/mods/944 |
| A game update can revert `bink2w64.dll` (same size as the original means reverted; the loader is ~227 KB) | **web~** (user comment) | same |
| SE and NML had a conflict after a March 2024 SE update; reported workarounds included moving SE's `DWrite.dll` into `NativeMods` | **web~** (comments; stale) | same |
| "Yet Another BG3 Native Mod Loader" (MolotovCherry, MIT): watcher or injector or autostart variants, "does not modify any game files", stores plugins in Larian's local data folder; claims compatibility with NML plugins | **web~** (README) | github.com/MolotovCherry/Yet-Another-BG3-Native-Mod-Loader |
| SE: `DWrite.dll` in `bin/` is only the installer/updater; the extender lives in `%LOCALAPPDATA%\BG3ScriptExtender` | **web✓** (Nexus App doc) + [src] `DivinityApp.cs:56-60`, CLAUDE.md §7 | |
| Manager identifies SE's `DWrite.dll` by `FileVersionInfo.ProductName` containing "Script Extender" | [src] `MainWindowViewModel.cs:524-543` | |

**Uncertainty flags:** whether NML still uses `bink2w64.dll` on the current game build; whether any current loader also proxies `DWrite.dll`
(which would collide with SE); NML's licence; how loaders order plugins. None of these are confirmed for 2026.

### 4.2 Skeleton

- **Phase 1, detect and report (read-only, low risk):** a "Native mods" panel listing `bin/*.dll` that are not part of the game install.
  Classify them: SE updater (ProductName check, as today), NML proxy (`bink2w64.dll` with `bink2w64_original.dll` beside it; size/version heuristic), other proxies (`dinput8.dll`, `version.dll`, `winmm.dll`: [inf] common proxy names, unverified for BG3), plus the contents of `bin/NativeMods/*.dll`.
  Warn on "NML proxy reverted by game update" and "unknown DLL in bin".
  *Getting the game's own DLL list:* hash-list per game version (cf. `IgnoredMods.json`), or "file not present in Steam's depot manifest" [inf]. Open question.
- **Phase 2, manage `bin/NativeMods` only:** enable or disable by moving between `NativeMods/` and a manager-owned `NativeMods.disabled/` (not renaming in place; [inf] some loaders might load `*.dll.disabled`?), install from archive through the §2.5 staging, and keep a backup of every replaced file.
  **Never write, rename, or delete `DWrite.dll`** except through the existing SE flow. Never install a loader automatically.
- **Phase 3 (maybe):** "Install Native Mod Loader" helper (NML or YA-NML) on explicit user action, with an uninstall that restores `bink2w64_original.dll`.
- Guards: refuse while the game runs (B12 / `:5424`); treat the Steam "verify files" path as an uninstall the user may trigger anytime [inf].
- **Security:** native mods are arbitrary code. Show a one-time warning, no auto-download of DLLs, and the `.dll/.exe` reject rule from §2.5 stays on for pak installs.
- Linux/Proton: DLL proxies need `WINEDLLOVERRIDES` (e.g. `bink2w64=n,b`) [mem]. The manager can only document this, not set it.

### 4.3 Decisions and open questions (9b)

- **Q-X1** Which loader(s) to support: NML, YA-NML, or loader-agnostic `NativeMods/` only?
- **Q-X2** Is detect-and-report enough for the owner and friends? Phase 2+ carries most of the blast radius.
- **Q-X3** Is native-mod state part of a Stage 8 order export and friend sync (DLLs in a shared bundle is a security decision)?
- **Q-X4** Can the 2024 SE+NML conflict still be reproduced on current SE? It needs a Windows test with both installed before anything ships.

## 5. 9c — Mod-page dependency and version checks

### 5.1 Two different things

1. **Local (`meta.lsx`), no network:** dependencies with UUID and `Version64` are already parsed (`DivinityModDataLoader.cs:250-275`).
   Missing deps are flagged by UUID only (`MainWindowViewModel.cs:1524-1531`). **Add "dependency installed but older than required"**: compare
   `installed.Version.VersionInt < dep.Version.VersionInt` (`DivinityModVersion2` operators, `:70-87`), ignoring a dep version of 0 and the
   base-game set (`DivinityModDataLoader.IgnoreModDependency`, also the Nexus App doc's vanilla-exclusion advice [web✓]). The tooltip and icon
   already exist (`MissingDependencyToolTip`, `DivinityModData.cs:170-172,376-379`). **Possibly upstreamable** as a bugfix-like improvement (Q-D1).
   Also consider order checks: a dependency placed *after* its dependent (the game loads dependencies first [web✓ "will try to load before the mod itself"]; whether misordering matters is Q-D2).
2. **Remote (mod page):** Nexus mod pages list "Requirements" (other Nexus mods, off-site links) [mem]. Whether v1 REST exposes them: **not confirmed**; probably GraphQL v2 only [inf] (Q-D3).
   mod.io has a mod dependencies endpoint [mem, unconfirmed]. Remote requirements are keyed by *page id*, not UUID, so they need §2.1's mapping in reverse (Nexus id → installed UUID), which only works for mods mapped already.

### 5.2 Skeleton

- Step 1 (local): outdated-dependency and dependency-order warnings. No network, no flags.
- Step 2 (remote, rides 9a.2): when a mapped mod's page lists a requirement that maps to no installed mod, add a row to the "new / missing" section of the Mod Updates panel (`IsNewMod`'s successor) with "Open page".
- Step 3 (with the downloader): "Install missing requirement", using §2.5, inserted *inactive*.
- Reconciling the two sources: `meta.lsx` is authoritative for *what the game will enforce*; the mod page is advisory (often lists SE, which is not a pak) [inf]. Show both and label the source.

### 5.3 Open questions (9c)

- **Q-D1** Upstream the local outdated-dependency check (it fits "bugfix/perf only" loosely) or keep it fork-only?
- **Q-D2** Should dependency order be enforced or only warned about? (`BuildOutputList(..., addDependencies = true)` at `DivinityModDataLoader.cs:1431` already injects deps on export: check how.)
- **Q-D3** Where do Nexus "Requirements" come from via the API (v1 vs GraphQL), and are they worth the extra calls?
- **Q-D4** Mods whose `meta.lsx` pins a dep `Version64` that the dep author never bumps: allow a per-mod "ignore version requirement"?
