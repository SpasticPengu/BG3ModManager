# S7: Stage 7 design, UI/UX refresh within AdonisUI

Fork-only (`ui/*`). Base: master at `fc35358`, with `origin/perf/list-render` (wt-perf) read for the Stage 6.1 overlap.
Written 2026-11-03. This container cannot build or run WPF, so nothing here has been rendered. Every claim cites
`path:line` (paths relative to `src/GUI/` unless they start with `src/`, `Core/` or a notes file). Anything marked **[inferred]** comes from
reading the source and has to be checked on Windows.

Reports folder status: `scratchpad/reports/` was empty when I started and when I finished, so no UI, VM2, S6 or AUDIT-PLAN report was available to cross-check.

Screenshot caveat: the only screenshot, `Screenshots/PreferencesWindow_GameDataPath.png`, predates the current source. It shows
labels like "Enable Story Log" and a bottom "Save" button. The source has "Story Log" (`src/Core/Models/DivinityModManagerSettings.cs:34`)
and a status bar in that slot (`Views/SettingsWindow.xaml:339-343`). It is still good evidence of layout, because the generator has not changed.

### Owner intentions this design assumes (gleaned)

- A modern-looking manager that you and friends enjoy using daily, published publicly, with no pressure to upstream UI work.
- Keep WPF and AdonisUI, and keep the diff reviewable. This is a restyle, not a rewrite. Light and Dark stay first-class and key-for-key identical.
- Get the list fast first (Stage 6), then make everything around it pleasant.
- Never fail silently. Your bug list (zip corruption, lost orders) is mostly "it went wrong and nobody said so", and R8 is the general case of that.
- Keep Linux reachable cheaply: behaviour goes in view models, toolkit-neutral choices where they cost nothing.
- Categories as flat divider rows, overrides folded into the order, multi-order export. The UI has to leave room for all three.
- Take ideas, never code or assets, from Redux. Upstream avalonia is a source of ideas only.

## 2. Visual direction

Goal: **quiet, dense, legible.** One brand accent (the existing purple `#4E38C9`), neutral AdonisUI layers, and status colour only where it means something. Every colour resolves through a key, so Light and Dark are just two value sets.

### 2.1 Type scale (theme-invariant, so new `Themes/Tokens.xaml`, not Light/Dark)

Today the code uses 11/16/18/20/24 plus the default 12 (grep). The new scale has five steps, all `sys:Double`:

| Key | Size | Weight | Use |
|---|---|---|---|
| `FontSize.Caption` | 11 | Normal | counts, secondary row text, setting descriptions |
| `FontSize.Body` | 12 | Normal | rows, controls (WPF/AdonisUI default; rows unchanged) |
| `FontSize.Subhead` | 14 | SemiBold | list headers ("Active Mods · 935"), Preferences category headers, divider rows (6.3) |
| `FontSize.Title` | 18 | SemiBold | dialog titles (replace 24 at `DeleteFilesConfirmationView.xaml:76`, `ExportOrderToArchiveView.xaml:75`, `HelpWindow.xaml:31`), busy-card title (replace 16 bold at `MainViewControl.xaml:101`) |
| `FontSize.Display` | 22 | Light | About window name only |

Font family stays the system default (Segoe UI on Windows). Do not hard-code it: Avalonia/Linux resolves its own. Remove the stray `FontFamily="Arial"` (`MainResourceDictionary.xaml:681`).

### 2.2 Spacing grid: 4 px base

The existing margins already cluster on 2/4/8 (grep: `Margin="4"` ×13, `"2"` ×9, `"8"` ×7). The tokens formalise that as `Thickness` and `sys:Double` in `Tokens.xaml`:

`Space.XS=2`, `Space.S=4`, `Space.M=8`, `Space.L=12`, `Space.XL=16`; plus `Pad.Control="8,4"`, `Pad.Button="12,4"`, `Pad.Card="12"`, `Gap.Toolbar="0,0,8,0"`.

Rules: icon buttons are 24×24 with a 16 px glyph (keeps `IconButtonStyle`, `MainResourceDictionary.xaml:88-96`). Toolbar groups are separated by `Space.L` instead of text labels. Window content padding is `Space.M`.

### 2.3 Colour tokens

How it works today: `App.xaml:5-6` merges `Themes/Light.xaml` and `Dark.xaml`. Each one merges an AdonisUI colour scheme (`Dark.xaml:7`, `Light.xaml:7`), and `MainWindow.UpdateColorTheme` swaps them per window (`Views/MainWindow.xaml.cs:325-345`). Custom keys follow the `ComponentResourceKey` pattern in `Themes/DivinityColors.cs`. New tokens go there as well. Adding members to the existing class is fine, because the no-prefix rule is about new types.

**Two kinds of token:**

- **Alias tokens** point at an AdonisUI key and need no new value. Views keep using AdonisUI keys directly. The table only fixes which one to use for each role.
- **Semantic tokens** are new keys with a value per theme. They go in **both** `Light.xaml` and `Dark.xaml`, in the same order (key-for-key). **Row-level brushes are written with literal colours and `po:Freeze="True"`**, not `Color="{DynamicResource …}"`. That matters for performance: commit `7fa83473` showed each redraw paying ~120 µs to register with an *unfrozen* shared brush (plan §6.1). Theme switching still works, because `UpdateColorTheme` replaces the whole dictionary and `DynamicResource` re-resolves to the other theme's frozen instance **[inferred; verify with Ctrl+L]**.

AdonisUI keys marked ✓ are already used in this repo (grep), so they exist in 1.17.1. Keys marked ? are AdonisUI names I expect to exist but must be checked against AdonisUI 1.17.1's `Colors`/`Brushes`/`Styles` classes before use.

## 5. Keeping a future Avalonia port cheap

1. **Views bind, VMs decide.** Today VMs reach into views: `ShowAlert → View.AlertBar` (`ViewModels/MainWindowViewModel.cs:4327-4337`), `_viewModel.View.AlertBar` (`MainWindowExceptionHandler.cs:32`), `View.DeleteFilesView.ViewModel` (`:4366-4369,5082,5371`). Every Stage 7 behaviour is a VM property or command (`NotificationCenter`, header texts, empty flags, `OpenFilterHelpCommand`, `ListDensity`). Code-behind is limited to toolkit glue, such as the storyboard start/stop.
2. **Semantic tokens, not toolkit tokens, in new markup.** Views reference `ModRowErrorBrush` and `TextSecondaryBrush`, and only `Light.xaml`/`Dark.xaml` map them to AdonisUI. Avalonia's `ResourceDictionary.ThemeDictionaries` Light/Dark carries the same names one-to-one (upstream avalonia already does this: `wt-avalonia/src/GUI/ModManager/Styling/ColorThemes/General.axaml:7-50`).
3. **Enums and bools, not MultiDataTriggers.** Avalonia has no `DataTrigger`, so replace `HasColorOverride`+`IsSelected` multi-triggers (`MainResourceDictionary.xaml:388-401`) with a `RowStatus` enum that maps to style classes on a port. No colour strings in Core.
4. **Vector geometry icons.** The same path data works in both toolkits.
5. **Settings metadata in Core attributes** (`Category`, `Kind`, `Order`). The generator is the only per-toolkit piece.
6. **No new Xceed or AdonisUI-only extensions in new UI.** In-window overlay dialogs follow the `DeleteFilesConfirmationView` pattern. Avoid `CursorSpotlight`/`Ripple` extensions, and avoid new `xc:MessageBox` call sites (22 exist; grep).
7. **System fonts and no `Effect`s.** Avalonia has `BoxShadow` on borders, not `DropShadowEffect` on text.
8. **No WPF grouping** (also R2).
