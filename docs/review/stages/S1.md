## 2. Versioning scheme

### 2.1 Decision: CalVer `YYYY.M.D.N`

Example: `2026.11.3.0`. `N` is the release counter for that day, starting at 0. No part has a leading
zero, and the tag is exactly `Version.ToString()`, so the tag is `2026.11.3.0` with no `v`.

Why this scheme:

- **It cannot collide.** Upstream `master` is on 1.0.12.x (F15) and `avalonia` has claimed 2.0.0.0
  (F16). A major of 2026 or higher is out of reach of any plausible upstream release. A `3.x` scheme
  would read like a successor to upstream, and that is exactly the impression to avoid.
- **It fits AutoUpdater and Windows.** It has four numeric parts and compares with `System.Version`
  (F8). Every part is ≤ 65534, the limit for `AssemblyVersion` and the 16-bit FileVersion fields.
  Same-day releases sort by `N`. Day 3 sorts below day 10 because `System.Version` compares parts as
  numbers.
- **It is a safety net.** The fork's version is always higher than upstream's. If a fork build were
  ever mis-pointed at upstream's feed, upstream's release would compare lower and would **not** be
  offered.
- **The tag style matches upstream.** Upstream uses bare numeric tags. `avalonia`'s future updater
  derives the version from the tag name with `Version.TryParse`
  (`wt-avalonia/src/Services/Services/External/GithubService.cs:40`,
  `AppUpdaterService.cs:59`), and bare numbers keep that option open.
- **The workflow can be filtered safely.** The pattern `20[0-9][0-9].*` never matches upstream's
  `1.*` tags. The local clone holds upstream's tags (F15), so an accidental `git push --tags` would
  not trigger fork releases.

The upstream base is recorded per release: in the release notes ("based on upstream 1.0.12.9 @
fc35358") and, optionally, in `<InformationalVersion>2026.11.3.0+upstream.1.0.12.9</InformationalVersion>`.
[unc] The .NET 8 SDK may append `.<commit>` to InformationalVersion on its own. That is harmless,
because nothing reads InformationalVersion today.

**Alternative, if the owner dislikes CalVer:** `10.<minor>.<patch>.0`, i.e. ordinary semver under a
major of 10. It has the same collision properties, but needs a policy for what bumps minor.

### 2.2 The four-file bump: script plus CI guard, not a props file

A `Version.props` would remove only two of the four places (`GUI.csproj:16-17`). `app.manifest` and
`Update.xml` cannot read MSBuild properties, so a script is needed either way. Making a props file
reach GUI also needs an `<Import>` in `src/GUI/Directory.build.props` (F14), and `GUI.csproj`
conflicts on every upstream version bump whether the fork edits lines 16-17 or deletes them.
**Recommendation:** keep the four places and make one script the only thing that writes them. CI
refuses any tag where they disagree.

`tools/release.py` is Python because Python is already a build dependency (`BuildRelease.py`,
`GUI.csproj:108`) and it works on Linux. Subcommands:

- `bump <ver>`: checks `^\d+\.\d+\.\d+\.\d+$`, that every part is ≤ 65534, and that the new version is
  higher than the current one. It then rewrites `GUI.csproj` `<AssemblyVersion>`/`<FileVersion>`, the
  `app.manifest` `assemblyIdentity version` and the `Update.xml` `<version>` and `<url>` (tag-pinned,
  §4.2). It edits **bytes** with anchored regexes, so the BOM and the LF/CRLF mix survive (F19), and
  it fails if any regex matches a count other than exactly once.
- `check [--tag T]`: all four values are equal and, if given, equal to T. `T`'s major is ≥ 2026. The
  `Update.xml` `<url>` equals `https://github.com/SpasticPengu/BG3ModManager/releases/download/T/BG3ModManager_Latest.zip`.
  `DivinityApp.cs` `URL_UPDATE` and `URL_CHANGELOG_RAW` contain `SpasticPengu/` and not `LaughingLeader/`.
  This is the regression net for R4, so a later upstream merge cannot silently repoint the URLs.
- `feed --tag T --zip Z --out dist/Update.xml`: copies the committed `Update.xml` and adds
  `<checksum algorithm="SHA256">` with the zip's lowercase hex SHA-256 (F6).
- `verify-zip Z`: checks the zip against required and forbidden lists (§4.3).
- `notes T`: extracts the `## T` section of `CHANGELOG.md` and fails if the section is missing.

Sketch of the byte-preserving core. It is Python, so CLAUDE.md's C# rules don't apply, but it uses
tabs like `BuildRelease.py`:

```python
import re, sys, hashlib
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent
TARGETS = [
	("src/GUI/GUI.csproj",   rb"(<AssemblyVersion>)[\d.]+(</AssemblyVersion>)"),
	("src/GUI/GUI.csproj",   rb"(<FileVersion>)[\d.]+(</FileVersion>)"),
	("src/GUI/app.manifest", rb'(<assemblyIdentity version=")[\d.]+(")'),
	("Update.xml",           rb"(<version>)[\d.]+(</version>)"),
]
VER = re.compile(r"^\d+\.\d+\.\d+\.\d+$")

def sub_once(path, pattern, value):
	p = ROOT / path
	data = p.read_bytes()                       # bytes: BOM and EOL untouched
	new, n = re.subn(pattern, rb"\g<1>" + value.encode() + rb"\g<2>", data)
	if n != 1:
		sys.exit(f"{path}: expected 1 match for {pattern!r}, got {n}")
	p.write_bytes(new)

def read_all():
	out = []
	for path, pattern in TARGETS:
		m = re.search(pattern.replace(rb"[\d.]+", rb"([\d.]+)"), (ROOT / path).read_bytes())
		out.append((path, m.group(2).decode() if m else None))
	return out
```

The owner's release flow becomes: `python tools/release.py bump 2026.11.3.0`, edit `CHANGELOG.md`,
one commit (`chore: release 2026.11.3.0`), `git tag 2026.11.3.0`, then
`git push origin fork/main 2026.11.3.0`. That pushes the named tag, **never `--tags`**. Update CLAUDE.md
§2.5 to say "never hand-edit; use `tools/release.py bump`".

## 4. Release pipeline

### 4.1 Shape

1. The owner runs the bump, commits and pushes the tag.
2. CI builds Publish on a clean Windows runner, verifies the result, and creates a **draft** release
   with all assets.
3. The owner downloads the draft and smoke-tests it.
4. The owner publishes the draft. That flip is the moment users are offered the release, so it is
   left as a deliberate human step.

### 4.2 Why the feed is a release asset (D1)

Option A, recommended: `URL_UPDATE = …/releases/latest/download/Update.xml`.
- The feed and the zip become visible atomically at publish.
- There is no bot commit and no write to `fork/main`, so branch protection can stay strict.
- Drafts and prereleases never reach users.
- Upstream already relies on the same redirect chain for the zip (F15), so the WebClient redirect
  behaviour is proven.
- Cost: fixing a broken feed means a new release. With immutable releases, assets are locked.

Option B: `URL_UPDATE = https://raw.githubusercontent.com/SpasticPengu/BG3ModManager/refs/heads/fork/main/Update.xml`
(the form works, F18).
- It needs a post-publish step that commits the checksummed `Update.xml` to `fork/main`.
- It has a window of up to 5 minutes of caching (F18) during which the feed and release disagree.
- If the feed ever named `releases/latest/download/…`, a version mismatch would cause an **endless
  update prompt**: the feed says X, the zip installs X−1, and the app offers X again.

The tag-pinned `<url>` (§3.2) removes that last hazard in both options.

### 4.4 Workflow sketch: `.github/workflows/release.yml` (on `fork/main` only)

```yaml
name: release
on:
  push:
    tags: ['20[0-9][0-9].*']          # never matches upstream's 1.x tags
permissions:
  contents: write                     # create release + upload assets
  id-token: write                     # build provenance
  attestations: write
concurrency: { group: release, cancel-in-progress: false }
jobs:
  release:
    runs-on: windows-2022
    environment: release              # optional: require the owner's approval to run
    env:
      TAG: ${{ github.ref_name }}
    steps:
      - uses: actions/checkout@v4     # pin to a commit SHA in the real file
        with: { submodules: recursive, fetch-depth: 0 }
      - name: Tag must be on fork/main
        run: git merge-base --is-ancestor $env:GITHUB_SHA origin/fork/main
      - name: Version consistency
        run: python tools/release.py check --tag $env:TAG
      - name: Parser tools (pinned)
        shell: pwsh
        run: |
          $zip = "$env:RUNNER_TEMP\gppg.zip"
          Invoke-WebRequest https://s3.eu-central-1.amazonaws.com/nb-stor/dos-legacy/ExportTool/gppg-distro-1_5_2.zip -OutFile $zip
          $h = (Get-FileHash $zip -Algorithm SHA256).Hash
          if ($h -ne '94B55A051200471ABA765D50404ABE66A14742913E224ADCB65B4E8383D2905A') { throw "gppg zip hash $h" }
          Expand-Archive $zip "$env:RUNNER_TEMP\gppg"
          $dst = 'External\lslib\External\gppg\binaries'
          New-Item -ItemType Directory -Force $dst | Out-Null
          Copy-Item "$env:RUNNER_TEMP\gppg\gppg-distro-1_5_2\binaries\*" $dst
      - uses: microsoft/setup-msbuild@v2
      - name: Pin SDK band
        run: '{"sdk":{"version":"8.0.400","rollForward":"latestFeature"}}' | Out-File -Encoding ascii global.json
      - name: Pre-generate LSLib parsers
        run: msbuild External\lslib\LSLib\LSLib.csproj -t:PreBuildStoryGppgFiles "-p:SolutionDir=$env:GITHUB_WORKSPACE\" -nodeReuse:false
      - name: Build Publish (also runs BuildRelease.py)
        run: msbuild BG3ModManager.sln -t:Build -p:Configuration=Publish -p:Platform=x64 -p:GeneratePackageOnBuild=false -restore -m -nodeReuse:false -bl:publish.binlog
      - name: Built assembly version == tag
        shell: pwsh
        run: |
          $v = [Reflection.AssemblyName]::GetAssemblyName("$PWD\bin\Publish\BG3ModManager.dll").Version.ToString()
          if ($v -ne $env:TAG) { throw "assembly $v != tag $env:TAG" }
      - name: Verify zip, make feed, notes, sums
        run: |
          python tools/release.py verify-zip BG3ModManager_Latest.zip
          python tools/release.py feed --tag $env:TAG --zip BG3ModManager_Latest.zip --out dist/Update.xml
          python tools/release.py notes $env:TAG > dist/notes.md
          Copy-Item CHANGELOG.md dist/CHANGELOG.md
          Get-FileHash BG3ModManager_*.zip -Algorithm SHA256 | % { "$($_.Hash.ToLower())  $(Split-Path $_.Path -Leaf)" } | Out-File -Encoding ascii dist/SHA256SUMS.txt
      - uses: actions/attest-build-provenance@v2   # [unc] check the current major
        with: { subject-path: 'BG3ModManager_*.zip' }
      - name: Draft release with all assets
        env: { GH_TOKEN: ${{ github.token }} }
        run: >
          gh release create $env:TAG --draft --verify-tag
          --title "BG3 Mod Manager (SpasticPengu fork) $env:TAG"
          --notes-file dist/notes.md
          BG3ModManager_Latest.zip "BG3ModManager_v$env:TAG.zip"
          dist/Update.xml dist/CHANGELOG.md dist/SHA256SUMS.txt
      - if: failure()
        uses: actions/upload-artifact@v4
        with: { name: binlog, path: publish.binlog }
```

- Publishing stays manual, after the owner's smoke test:
  `gh release edit <tag> --draft=false --latest`. Creating as a draft and then publishing is also the
  order immutable releases require [web: assets must be attached before publication].
- No secrets beyond `GITHUB_TOKEN`, and no `pull_request` trigger.
- Actions on a fork are **disabled until enabled once** in the Actions tab [web].
- The `binlog` is uploaded only on failure.

Ideas only, from avalonia: upstream's rewrite dropped Autoupdater.NET's XML feed for
`AutoUpdateViaGitHubRelease` driven by the latest release's tag
(`wt-avalonia/src/Services/Services/AppUpdaterService.cs:36,52-66`). Its download path does no hash
check. The useful takeaway is "the GitHub release is the source of truth", which Option A adopts
without changing libraries.

## 5. Checksum, HTTPS and the compromised-account question

**What `<checksum algorithm="SHA256">` protects against:**
- A corrupted or truncated download being extracted over the install.
- A feed that names one release while the URL serves another. Tag pinning makes this unlikely;
  checksumming makes it impossible to install.
- An asset swapped after publication by anyone who cannot also rewrite the feed. With immutable
  releases on, assets cannot be swapped at all [web].
- On mismatch, AutoUpdater shows an error box and installs nothing (F6). With the F10 fix the app
  stays open.

**What it does not protect against:** anyone who can write the feed. The feed and the zip come from
the same account and the same release. TLS already covers transport. Use `SHA256` exactly, because
omitting the attribute means MD5 and lower-case `sha256` throws (F6).

**HTTPS-only.** `URL_UPDATE` is an HTTPS constant. The download URL comes from the feed, so
`IsTrustedUpdate` enforces the HTTPS prefix, this fork's release path and `.zip` (§3.3).
AutoUpdater's TLS `ServicePointManager` tweak (`AutoUpdater.cs:302-308`) does nothing on .NET 8.
[inf]

**What a compromised GitHub account, or a stolen token with `contents:write`, could still do:**

1. **Ship malware to every fork user.** It can publish a release with a trojaned zip and a
   self-consistent checksummed feed. Users see a normal "update available" prompt. One click runs
   ZipExtractor and replaces the app as the user (F7, F11). Neither the checksum, immutable releases,
   provenance nor the URL allowlist stops this: an attestation proves only that "this workflow built
   this commit", and the attacker controls the commit.
2. Push a backdoor to `fork/main` that the owner's next legitimate release ships unknowingly.
3. Delete releases. Updates then stop. With the F9 fix this is visible on F7; otherwise it looks like
   "up-to-date".
4. Rewrite the README download links to point elsewhere.
5. It **cannot** force a silent install. The custom handler always asks (F5), and `mandatory` is
   ignored. It also cannot make the app execute a non-zip, because of `IsTrustedUpdate`.

**Mitigations, cheapest first:**
- Use a passkey or hardware key for 2FA.
- Audit and prune PATs and OAuth apps. The `gh` token on the owner's PC is a credential.
- Enable **immutable releases**.
- Add a **tag ruleset** (`20*`, restrict creation and deletion) and a **branch ruleset** on `fork/main`.
- Use a `release` environment with a required reviewer.
- Pin Actions to commit SHAs and let Dependabot update them.

**The only real defence against item 1 is a signed feed with a key that never touches GitHub.** It is
deferred (decision D2) and sketched here:
- Sign `Update.xml` locally with an ECDSA P-256 key, which .NET 8 supports natively.
- Upload `Update.xml.sig`.
- Embed the public key in `DivinityApp`.
- Verify through `AutoUpdater.ParseUpdateInfoEvent`, which receives the raw feed text
  (`AutoUpdater.cs:415-425`) on the background worker: fetch `.sig`, call `ECDsa.VerifyData` over the
  UTF-8 bytes, and throw on mismatch so it surfaces through the F9 path.

The checksum inside a signed feed then binds the zip. Cost: every release needs one local signing
step after the CI draft. Authenticode signing is the conventional alternative, but 1.9.2 never checks
it for zips (F7), so it would need app-side verification too. [unc] I did not confirm free OSS
signing programmes or their eligibility.

## 6. Verification: "with a low AssemblyVersion, the updater offers your release, not upstream's"

Why the version must be **lower than both**: with `1.0.0.1`, upstream's feed would offer `1.0.12.9`
and the fork's feed offers `2026.x`, so the **version string shown** tells you which feed was read.
A version between the two would make "nothing offered" ambiguous, because a failed fetch also looks
like "up-to-date" until F9 is fixed.

Preconditions:
- `chore/fork-identity` and `fix/update-check-errors` are merged into `fork/main`.
- Release `R` = `2026.11.3.0` is **published** and marked Latest, with assets `Update.xml`,
  `BG3ModManager_Latest.zip` and `CHANGELOG.md`.
- `curl -sL https://github.com/SpasticPengu/BG3ModManager/releases/latest/download/Update.xml` prints
  the `2026.11.3.0` feed with a `<checksum algorithm="SHA256">`.
- Run `curl -sL …/releases/latest/download/BG3ModManager_Latest.zip | sha256sum` and confirm the hash
  equals that checksum.

Steps:
1. `git switch fork/main`. Edit **only** `src/GUI/GUI.csproj:16-17` to `1.0.0.1` and don't commit.
   AutoUpdater uses the assembly version (F4), so the manifest does not matter here.
2. Build `PublishTest|x64` (same output as Publish, no zip), so the `_Lib` resolver is exercised
   (risk R5).
3. Copy `bin\PublishTest\` to a scratch folder such as `D:\BG3MM-updtest\`, not Program Files and not
   your real install. Create an empty file named `debug` there to turn logging on (CLAUDE.md §5).
4. Launch it. The title should read `… 1.0.0.1`.
   - **Pass:** after loading, the update window says "… 2026.11.3.0 is now available. You have version
     1.0.0.1 installed."
   - **Fail A:** it offers `1.0.12.9`. The build still reads upstream; check `URL_UPDATE`.
   - **Fail B:** "up-to-date", or an "Update check failed" alert. Read `_Logs\`; the feed is missing
     or unreachable.
5. Press **F7**. The same window appears, plus the "Update found!" alert.
6. Optional network proof: with Fiddler Classic (HTTPS decryption on), confirm a GET to
   `github.com/SpasticPengu/BG3ModManager/releases/latest/download/Update.xml` and **no** request to
   `raw.githubusercontent.com/LaughingLeader/…`.
7. Click **Update**. The download dialog runs, the checksum passes, the app exits, ZipExtractor
   replaces the files, and the app restarts with the title `… 2026.11.3.0`. F7 now says
   "up-to-date". Confirm `D:\BG3MM-updtest\Data\settings.json` survived; the zip ships no `Data/`.
8. **Negative tests.** Each is a temporary local edit of `URL_UPDATE` to a `file:///D:/BG3MM-updtest/feed.xml`
   you control. [inf] WebClient accepts `file://`; if it doesn't, use a secret gist's raw URL.
   - (a) Correct URL, wrong checksum → "File integrity check failed", the app stays open (F10 fix),
     and no files change.
   - (b) `checksum` element removed → "Ignoring update … no SHA256 checksum".
   - (c) URL on another host or `http://` → "Ignoring update … not from this fork's GitHub releases".
   - (d) URL ending in `.exe` → refused.
   - (e) Feed URL 404 → "Update check failed" on F7.
9. Revert: `git restore src/GUI/GUI.csproj src/Core/DivinityApp.cs`, then confirm `git status` is
   clean. Delete the scratch folder.

Also run the cheap static guard on every PR into `fork/main`:
`python tools/release.py check` fails if any `LaughingLeader/` URL comes back in `URL_UPDATE` or
`URL_CHANGELOG_RAW`, for example after an upstream merge.

## 7. Pre-public-release checklist

**Repository and GitHub settings**
- [ ] Create `fork/main` on origin. It does not exist yet (F17).
- [ ] Make `fork/main` the **default branch**. Visitors otherwise land on `master`, which carries
      upstream's README ("only official source").
- [ ] Turn on Issues. Decide on Discussions (D4) and make `config.yml` match.
- [ ] Turn on Actions (fork default: off), immutable releases, a tag ruleset `20*`, a branch ruleset on
      `fork/main`, and the `release` environment with yourself as required reviewer.
- [ ] Set up 2FA with a passkey or hardware key. Review PATs and authorised OAuth apps.

**Code** (`chore/fork-identity` merged)
- [ ] `DivinityApp.cs` constants (§3.1), `Update.xml` (§3.2) and the `IsTrustedUpdate` guard (§3.3).
- [ ] `fix/update-check-errors` merged into `fork/main` and offered upstream as a PR from `master`.
- [ ] `fix/publish-prebuild-quoting` merged. Clean-checkout traps either fixed upstream in the
      submodules or covered by the CI workarounds in §4.3.
- [ ] README (§3.4), LICENSE untouched except an optional added line, About window and tooltips (§3.5),
      issue templates (§3.6).
- [ ] `grep -rn -i 'laughingleader' src .github README.md Update.xml` leaves only intended credit,
      upstream and donation references.
- [ ] No test hooks in release code: perf drivers (`perfscroll`), temporary logging. `verify-zip`
      enforces the file side.

**Release**
- [ ] `CHANGELOG.md` has a `## 2026.x.y.z` section including "based on upstream 1.0.12.9 @ fc35358".
- [ ] `release.py bump`, then commit, then tag. Push the branch and **that tag only**.
- [ ] CI is green and the draft has 5 assets: both zips, `Update.xml` with a SHA256 checksum,
      `CHANGELOG.md` and `SHA256SUMS.txt`.
- [ ] Smoke-test the draft zip in a scratch folder against the real mod folder, then boot the game
      once with an exported order.
- [ ] Publish (`--latest`) and run the §6 procedure against the published release.
- [ ] **Never hand anyone a build made before Stage 1.** Those builds still read upstream's feed and
      will replace themselves on upstream's next release. If any are out there, tell those friends to
      switch off Settings → "Automatically Check For Updates" or to install the fork release.
