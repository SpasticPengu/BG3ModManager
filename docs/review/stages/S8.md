## 0. TL;DR

1. **The bundle is still an ordinary zip that upstream can read.** Order files go in
   `orders/<name>.json` in the exact upstream `DivinityLoadOrder` shape. Pak files go in
   `paks/<uuid>/<version64>/<original file name>`. A manifest named `bundle.manifest` holds schema
   version, mod table (UUID, Version64, size, SHA-256, part files), per-order version pins, overrides
   and what was left out. The manifest is JSON but **must not end in `.json`**: upstream turns every
   `*.json` in a zip into an order (MWVM:3457-3468, 3511).
2. **Dedupe is by UUID, and the "two versions" case can't happen in a local export.** An install
   holds exactly one mod per UUID (`SourceCache` keyed by UUID, MWVM:82). The loader keeps the highest
   duplicate (`DivinityModDataLoader.cs:789-806`). Order entries carry no version at all
   (`DivinityLoadOrder.cs:8-21`). Two versions can only meet when bundles are merged or synced. v1
   policy is **one version per UUID per bundle**. The schema keys mods by `modKey`
   (`uuid@version64`), not by UUID, so a later library or hardlink design (task LIB) can carry
   several versions without a schema break.
3. **Stage 2 seam:** split export into *snapshot on the UI thread* → *pure writer
   `WriteOrderArchiveAsync(orders, mods, output, entryNamer, progress, token)`* → *alert shell*. This
   fixes E1-E6 on the way. Stage 8 then only adds a manifest, a namer and a picker UI.
4. **Large exports:** store paks uncompressed (paks are already compressed inside **[inference]**).
   Set per-entry zip64 for files ≥ 4 GiB (verified: without it SharpCompress 0.39 *throws*, and E2
   swallows the error). Stream through `WriteToStream` + `CopyToAsync(…, token)` for byte progress
   and cancellation inside a file. Hash while writing. Write the manifest last. Write
   `<target>.partial`, then move it over the target.
5. **New defects found in passing:** **E7**, multi-part paks (`Foo_1.pak`…) are never exported.
   **P1**, override mods without `meta.lsx` use their *full path* as UUID, so the Windows user name
   leaks into any exported order or manifest. Also: an upstream build can't import **any** archive
   over 2 GiB (MWVM:3412), whatever its format.
6. **Sync builds on the same manifest.** First ship a pak-free "share orders" file with a diff view
   and a co-op readiness check. Next, a content-addressed shared-folder publish/subscribe
   (Syncthing, OneDrive, Dropbox). Then read-only URL subscriptions (gist or GitHub raw).
   Writing to GitHub comes last.

## 1. Owner intentions this design relies on (what I gleaned)

From the plan, the overview, CLAUDE.md and this task's brief:

- A public fork, **mainly for you and your friends**. The real use case behind "order syncing with
  friends" is very likely **co-op multiplayer**, where everyone needs the same mods at the same
  versions **[inference]**. That is why pins default to *exact*.
- **No server you have to run.** Transports must use what friends already have: a shared folder or
  cloud drive, a GitHub repo or gist, a URL.
- **A big library**: 1 121 mods, 935 active, **27 GB**. Anything per-mod or per-byte has to scale to
  that, and cancelling must be safe.

- **Redux gives ideas only.** The avalonia branch is also ideas only (§10).
- House style: tabs, CRLF, BOM, Allman, `var`, no `string?` in Core/GUI, unprefixed new types,
  `[DataMember]` + `[Reactive]` + `[SettingsEntry]` for any setting, menu items through

**SharpCompress 0.39.0 behaviour (verified by reading the tagged source, downloaded to
`scratchpad/dl-sharpcompress/`):**
- `ZipWriterOptions.UseZip64` doc: "If this is not set, individual stream lengths cannot exceed
  4 GiB … Archives larger than 4GiB are supported as long as all streams are less than 4GiB"

  ≥ 4 GiB (`ZipCentralDirectoryEntry.cs:43-50`, `ZipWriter.cs:237-280`).
- A single entry ≥ 4 GiB without zip64 throws `NotSupportedException("Attempted to write a stream
  that is larger than 4GiB without setting the zip64 option")` (`ZipWriter.cs:451-455, 522-533`).
  **Today that exception is swallowed by E2, and the mod silently drops out of the archive.**
- Each entry can set its own `CompressionType` and `EnableZip64`, and can be written as a stream
  through `WriteToStream(path, ZipWriterEntryOptions)` (`ZipWriterEntryOptions.cs`,
  `ZipWriter.cs:82-121`). Zip64 needs a seekable output. `FileStream` is seekable.
- `NormalizeFilename` **removes everything up to the first `:`** in an entry path

  path (see P1).

### 2.3 Multi-part paks: new defect E7

LSLib packages can be split into `<base>_<n>.pak` parts (`External/lslib/LSLib/LS/PackageReader.cs:54-57`,
`Package.MakePartFilename` :85-90). The loader deliberately skips part files
(`DivinityModDataLoader.cs:430-444`). Export only writes `mod.FilePath` (MWVM:3598). **A multi-part
mod is exported without its parts** and imports broken. How common multi-part *mods* are is
**[inference: rare, likely large texture packs]**. The fix costs little: list the parts (read
`NumParts` from the header, or probe `_1`, `_2`… until one is missing), then write them all.

### 2.4 Privacy defect P1

CLAUDE.md §6: "override paks with no `meta.lsx` get `UUID = <full pak path>`". Those mods are
force-loaded and go into every archive export (MWVM:3573). If one ever lands in an order (through
`ForceAllowInLoadOrder`), the order JSON contains `C:\Users\<name>\AppData\...`. Any manifest that
records UUIDs has the same problem. **Rule: a UUID that is not a GUID is never written raw.** Write
`ovr:<sha256(uuid)[0..16]>` plus the bare file name (§3.3).

### 2.5 Existing scaffolding to revive

`src/GUI/ViewModels/ExportOrderToArchiveViewModel.cs` + `Views/ExportOrderToArchiveView.xaml` are a
**never-instantiated** `BaseProgressViewModel` with per-mod checkboxes, `IncludeOverrides` and an
`ExportOrderFileType` enum. `Run()` is a stub (`:61-67`). Nothing outside the two files references
them (grep). The overlay pattern to follow is `DeleteFilesConfirmationView`, hosted in
`MainViewControl.xaml:132` with `Panel.ZIndex="99"`. It inherits the main window's theme resources,
so **no new window and no `UpdateColorTheme` line are needed**.

## 3. Archive format v1 ("order bundle")

### 3.1 Layout

```
MyOrders-2026-11-03_14-30-00.zip
├─ README.txt                          plain text: what this is, how to install by hand (ignored by every importer)
├─ orders/
│  ├─ Co-op Run.json                   upstream DivinityLoadOrder shape, Stored (no compression)
│  ├─ Solo Tactician.json
│  └─ Pengu_Current.json               the profile's Current order, renamed (see 3.4)
├─ paks/
│  ├─ 0f1c...-...-c2e1/36028797018963968/ExampleMod.pak          Stored
│  ├─ 0f1c...-...-c2e1/36028797018963968/ExampleMod_1.pak        part file of the same mod
│  ├─ 9a77...-...-0b13/36310271995674624/ExampleMod.pak          a different mod with the same file name: no collision
│  └─ _overrides/ovr-3f9a1c0b7d2e4a55/0/SomeOverride.pak
└─ bundle.manifest                     JSON, Deflate, written LAST
```

- **Pak folders use `uuid/version64`**, so the key is identity, not `Path.GetFileName`. The original
  file name is kept as the leaf. That keeps manual extraction readable, and **an upstream build still
  installs paks under their real names** (it flattens by `GetFileName`). For non-GUID UUIDs (P1) the
  folder is `_overrides/ovr-<sha256(uuid)[0..16]>/0/`.
- `orders/` file names are made unique **case-insensitively** across the archive. Upstream keys
  orders by base name (MWVM:3468), and Windows extraction folds case. Use `MakeSafeFilename` plus a
  ` (2)` suffix on collision. Also reject reserved device names (`CON`, `NUL`…) and trailing
  dots/spaces, which `MakeSafeFilename` (`DivinityModDataLoader.cs:57-64`) does not handle.
- Order JSONs are **Stored**. They are tiny, and an uncompressed entry stream makes upstream's single
  `ReadAsync` (I1, MWVM:3464) much more likely to fill the buffer
  **[inference: free mitigation for upstream readers; test with a 935-entry order]**.

### 3.2 Order JSON: unchanged

Exactly what `JsonConvert.SerializeObject(order)` produces today: `{"Order":[{"UUID":…,"Name":…}]}`.
The fork's own `Orders/*.json`, upstream's importer and "Import order from file" all read it as it
is. Version pins live in the manifest, not in the order, so a plain order file never changes meaning.
Stage 6.3 divider entries pass through untouched. The mod union ignores them by id scheme (S6.3
decides the scheme; S8 only needs an `IsDivider(entry)` predicate).

### 3.3 `bundle.manifest` (schema v1)

The name is not `*.json` (upstream would import it as an empty order) and not `*.pak`. It is
Deflate-compressed and written after every payload entry, so hashes are known. The fork reads it
through the central directory (random access), so its position at the end costs nothing.

- `modKey` = `<uuid>@<version64>` (or `ovr:<hash16>@0`). The mod table is **keyed by modKey, not
  UUID**, so a future bundle can hold two versions of one mod (LIB task, or a sync stash) without a
  schema change. v1 writers emit at most one key per UUID.
- `pins` say which modKey each order entry was exported against. An entry whose mod is in the bundle
  but has no pin means "any version". `missing` lists entries the exporter did not have installed.
- `payload`: `"embedded"` (paks in this zip), `"none"` (share-orders file, §8.1) or
  `"content-addressed"` (shared folder, §8.2). One schema covers all three.
- `sources` comes from `DivinityModData.GetAllURLs()` (`DivinityModData.cs:273-292`). It is what a
  friend without the pak gets: a link.
- Never written: `FilePath` of any mod, raw non-GUID UUIDs, settings, the Nexus API key, profile
  folder paths. See §9.
- `revision` and `revisionId` (hash of the canonical `orders` + `pins` sections) exist for sync
  change detection and the three-way base (§8.4). A one-off export sets `revision: 1`.

### 3.4 Naming the Current order

Upstream treats an imported order *named* `Current` as "overwrite the active order" (MWVM:3112),
through the suspicious `SetFrom` path (§2.2). The multi-order export therefore writes the profile's
Current order as `<Profile>_Current.json`. That matches upstream's own archive naming at
MWVM:3561-3565. The manifest sets `isModSettings: true`, and the fork importer offers "apply to
active profile" as an explicit choice. The single-order Ctrl+R export keeps its current naming in
the upstream PR (no behaviour change there).

## 4. Dedupe rules and the version policy

### 4.1 Building the export set (in order)

1. **Snapshot on the UI thread:** call `UpdateOrderFromActiveMods()` (also fixes the Ctrl+R
   staleness), then clone each selected order (`DivinityLoadOrder.Clone()`, `:304-312`) and capture
   the matching `DivinityModData` references into plain lists. The background writer never touches
   bound collections.
2. **Union by UUID** (ordinal, matching the `SourceCache` key at MWVM:82) across all selected orders'
   entries. Skip divider entries and Larian/builtin mods (they are not in `Mods`, MWVM:120).
3. **Overrides** (`ForceLoadedMods` where `!IsForceLoadedMergedMod`) are **bundle-level**, not
   per-order, matching today's behaviour (MWVM:3573). The picker's `IncludeOverrides` switch already
   exists (`ExportOrderToArchiveViewModel.cs:38, 104-113`).
4. **Entries not installed locally** go to `orders[i].missing`, with no payload.
5. **User-unticked mods** go to `notIncluded` with reason `user-excluded`. The order JSON still lists
   them; only the payload drops them.
6. **Physical-file dedupe:** if two mod records resolve to the same `FilePath` (case-insensitive full
   path), write the file once and reference it from both `files[]` **[inference: shouldn't happen
   for normal paks; cheap insurance]**.
7. **Part files:** add `_1…_n` parts to the mod's `files[]` (E7).
8. **Editor mods:** pack once into the temp dir as today (MWVM:3601-3626) with `kind: "editor"`.
   The version is whatever `meta.lsx` says.

### 4.2 Two orders, different versions of one mod: explicit policy

- **Local export: can't happen, by construction.** There is one `DivinityModData` per UUID
  (MWVM:82), the loader keeps only the highest-versioned duplicate and hands the rest to the
  delete-duplicates flow (`DivinityModDataLoader.cs:789-806`, MWVM:4366), and
  `DivinityLoadOrderEntry` has no version field (`DivinityLoadOrder.cs:8-21`). So every order in one
  export pins the same modKey. The writer **asserts** this: one modKey per UUID, or abort with a
  bug alert.
- **Merged or synced bundles (Stage 9) and LIB:** two versions really can meet. v1 rule: **one
  version per UUID per bundle**, chosen as follows:
  1. if the user picked one in the conflict UI, use it;
  2. otherwise the **highest `version64`** (same rule the loader uses, so no surprise after a
     refresh);
  3. on equal `version64` with different `sha256`, the **newest `lastWriteUtc`**, and the order row
     gets a ⚠ badge "same version, different file".
  Orders pinned to the version that lost keep their pin. The import preview and the diff show
  "pinned X, bundle carries Y". The choice is never silent.
- **Why not carry both?** The manager and the game can only have one pak per UUID active. Two paks
  with one UUID in `Mods/` become "duplicates" (above). Carrying both only helps once something swaps
  files per order. That is LIB's per-order deployment, and the modKey-keyed schema already allows it.

## 5. The Stage 2 refactor that makes Stage 8 cheap (upstreamable)

Stage 2 stays on `fix/zip-export-corruption` from `master`, with the minimal diff in MWVM plus a
small writer class. Shape:

| Fix | How |
|---|---|
| E1, E3 | `var tempPath = outputPath + ".partial";` opened with `new FileStream(tempPath, FileMode.Create, FileAccess.ReadWrite, FileShare.None, 1 << 20, FileOptions.Asynchronous)`. The target is never opened until the move. Same directory, so the move is a rename. |
| E2 | Per-file `try { … } catch (OperationCanceledException) { throw; } catch (Exception ex) { result.Failures.Add(...) }`. The shell shows `ShowAlert` naming each failed mod. The manifest records them as `notIncluded/read-error`. |
| E4 | No `Task.Factory`. `using var entry = zip.WriteToStream(name, opts); await src.CopyToAsync(entry, 1 << 20, token);`. Cancellation now works *inside* a 2 GB pak, not only between mods. |

The MWVM shell becomes `ExportOrdersToArchiveAsync(IEnumerable<DivinityLoadOrder> orders, bool includeOverrides, string outputPath)`:
it snapshots (§4.1), calls the writer on the taskpool, and alerts on the main thread. Ctrl+R and
"Export As" both call it with `new[] { SelectedModOrder }`, so the upstream PR changes no behaviour
beyond the fixes. **This is the whole reason to do it in Stage 2:** Stage 8 adds a list of orders, a
namer and a trailer, and nothing else in the writer changes.

### 5.1 Throughput for 27 GB **[inference: measure in Stage 8 verification]**

- Today: Deflate, single-threaded. Deflate runs at tens of MB/s per core, so 27 GB is roughly
  **6-15 minutes CPU-bound**, for very little gain (BG3 paks compress their contents internally).
- Stored: limited by disk. On one NVMe, roughly 1 GB/s read+write, so **about 30-60 s**. On an HDD
  at 100-150 MB/s, about 3-5 min.
- SHA-256 while streaming (`IncrementalHash.CreateHash(HashAlgorithmName.SHA256)`, fed from the same
  1 MiB buffer): about 1-2 GB/s with SHA-NI, hidden under disk I/O on most machines. If it measures
  slow, `System.IO.Hashing.XxHash128` is the fallback for change detection, with SHA-256 kept only
  for sync.
- **Hash cache** `Data/pak-hashes.json` keyed by `(full path, length, lastWriteUtc)`. Re-exports and
  every sync comparison skip re-hashing unchanged paks. Sync needs this; reading 27 GB at every
  startup is not an option.
- Progress UI: `IProgress<ArchiveExportProgress>` (bytes done/total, current mod, index/count)
  reported at most every 100 ms to `MainProgressValue`/`MainProgressWorkText`. Example: "Adding
  Example Mod (312/935), 12.4 of 27.0 GB". `CanCancelProgress`/`MainProgressToken` stay as they are.

## 6. Import UX (fork, Stage 8)

### 6.1 Flow

1. **Open.** File → "Import Order & Mods from Archive…" (existing `Keys.ImportOrderFromZipFile`,
   MWVM:5017) or drag-drop. If the zip has `bundle.manifest`, go to **preview**. If not, use the
   legacy path (§7.2). Drag-drop of a bundle (`onlyMods: true` today, MWVM:1871) also opens the
   preview instead of ignoring its orders.
2. **Preview (nothing written yet).** An overlay `ImportBundleView` sits on `MainViewControl` like
   `DeleteFilesConfirmationView` (themed for free). Its VM `ImportBundleViewModel :
   BaseProgressViewModel` holds all logic, so Linux and Avalonia stay cheap.

   **Orders pane:** one row per order. Columns: checkbox, name, entry count, "N not available after
   import", and a conflict action:
   - no local order of that name → *Import*;
   - name exists → **default *Import as "Co-op Run (from Pengu 2026-11-03)"***, with *Replace
     existing* and *Skip*. Replace goes through `CreateSnapshot` undo, like `AddNewModOrder`
     (MWVM:2037-2066). Imported orders get an explicit `FilePath` at once, so a later save can't
     overwrite another order's file (§2.2);
   - `isModSettings` order → default *Import as new order*, with an opt-in *Apply to active profile
     (Current)*. That loads it into Current through `SetOrder` (not `SetFrom`). Nothing reaches
     `modsettings.lsx` until the user exports to the game, as today.

   **Mods pane:** the union of mods pinned by the **checked** orders, plus overrides if included.
   Unticking an order unticks mods used only by that order; reverse dedupe uses the same union
   function as export. Status compares the manifest with the local `mods` cache (and the hash cache
   when versions match):

   | Status | Default action |
   |---|---|
   | New | Install |
   | Identical (same `version64`, same `sha256` or same size+version if no cached hash) | Skip. Re-importing a 27 GB bundle writes only what changed |
   | Theirs newer | Update (old file moved to backup) |
   | Theirs older | **Keep mine** (option: install theirs). Matters for co-op exact match |
   | Same version, different file | Ask, default keep mine, ⚠ |
   | Not in bundle (missing or excluded by sender) | Show `sources` links |
   | File name clashes with a *different* local mod | Install as `OutputPakName` (`Folder_UUID.pak`) |

   **Footer:** "Will write 14 files (3.2 GB), skip 921 unchanged, back up 3. Free space on Mods
   drive: 40 GB". Options: *Add imported mods to active list* (existing `toActiveList` param) and
   *Back up replaced paks* (default on).
3. **Run.** Each file is extracted to `Path.GetTempPath()/BG3MM-Import-<guid>/` while hashing. A
   hash or size mismatch fails that file. The file is then moved to `Mods/<fileName>`. The temp dir
   is on the same volume in the default Windows setup, so the move is a rename; otherwise it copies,
   which is slower but still correct. Never stage *inside* `Mods/`: the loader scans it recursively
   (`DivinityModDataLoader.cs:757-761`). Replaced files go to
   `<app>/_Backups/<date>/<original name>` first. Then `LoadModDataFromPakAsync` on the final file →
   `AddImportedMod`. Errors go per file to `ImportOperationResults` + `ShowAlert` + the existing
   `_Logs/ImportOrderFromArchive_*_Errors.log` (MWVM:3093-3099).
4. **Safety:** output names come **only** from the manifest's `fileName`, passed through
   `Path.GetFileName` + `MakeSafeFilename` + reserved-name and `..` rejection. Never from entry paths
   (no zip-slip). Bytes written are capped at the manifest `size`, which defeats zip bombs.

## 7. Compatibility

### 7.1 Upstream build importing a fork multi-order bundle (behaviour read from MWVM:3391-3524)

| Case | Result |
|---|---|
| Bundle ≥ 2 GiB | **Fails entirely** on any upstream build without the Stage 3 I3 fix (MWVM:3412). The cause is the archive size, not our format. Mitigation: the export picker offers "Orders only (no mod files)", which gives a KB-sized zip that any build imports |
| Bundle < 2 GiB | Works. Paks flattened by real file name; `orders/*.json` imported as named orders; `bundle.manifest` and `README.txt` ignored (neither `.pak` nor `.json`) |
| Two versions of the same file name in one bundle | Only in merged bundles; upstream keeps whichever comes last (I5). Acceptable and documented |
| `<Profile>_Current.json` | Imported as an ordinary order. Doesn't hit upstream's destructive `Current` path |
| Large order JSON | Stored entries make I1 unlikely **[inference]** |
| Divider entries (S6.3) | Shown as missing mods by upstream. Harmless, and S6.3's concern (R7) |

### 7.2 Fork build importing an old single-order zip (no manifest)

Legacy mode: build a `OrderBundleManifest` in memory from the zip:
- orders = every `*.json` that deserializes to a `DivinityLoadOrder` **with `Order.Count > 0`**
  (drops junk JSON, fixes the "empty order named settings" case), named by base name. Duplicate
  base names get suffixes instead of being thrown away;
- mods = every `*.pak`, with identity unknown until extracted. The preview shows file names and
  sizes, and statuses resolve after extraction to the temp dir (read meta there, then decide
  skip/replace before the move). Same UI, with a "contents identified during import" note;
- `Current.json` → treated as `isModSettings` (default: import as new order).
- Optional, cheap: accept an `"Entries"` array as an alias for `"Order"`, because the upstream
  avalonia branch renamed the property (`wt-avalonia/src/Core/Models/Mod/Order/ModOrder.cs:23, 321-334`).
  This is a format observation, not code reuse.

### 7.3 Forward and backward compatibility of the manifest itself

- Readers accept `schemaVersion > supported` **if** `minReaderVersion <= supported`, ignoring unknown
  fields (Newtonsoft default) and preserving them (`[JsonExtensionData]`) when re-writing.
- If `minReaderVersion > supported`, fall back to legacy mode with a warning: "made by a newer
  version; importing mods and orders without version information". The layout is always readable
  without the manifest, so data is never stranded.
- Bump rules: adding optional fields doesn't bump `minReaderVersion`. Changing the meaning of an
  existing field or the layout does.

## 8. Stage 9: syncing with friends on top of this format

### 8.1 Payload: one schema, three payload modes

- **`payload: "none"` "share orders" file.** `MyOrders.bg3share`: a small zip holding `orders/*.json`
  + `bundle.manifest` with pins, sizes, hashes and `sources`, but no paks. Tens of KB for 935 entries,
  so it fits in a Discord message (Discord's free upload limit is small; a full bundle never fits).
  Upstream can import it as orders only.
- **`payload: "embedded"`**: the Stage 8 zip.
- **`payload: "content-addressed"`**: a folder, below.

### 8.2 Transports that need no server you run

| Transport | Carries | How | Caveats |
|---|---|---|---|
| **Shared folder / sync tool** (Syncthing, OneDrive, Dropbox, Google Drive, a LAN share) | orders + paks | "Publish to folder" writes `<share>/<publisher>/share.manifest`, `orders/*.json`, `objects/<sha[0..2]>/<sha256>.pak`. **Content-addressed**, so publishing after one mod update copies one file, not 27 GB. Manifest written last via temp+rename. "Subscribe to folder" reads the manifest, verifies each object's size and hash before install, and treats mismatches as *not synced yet, retry*. Per-publisher subfolders avoid sync-client conflict copies when several friends publish | Free cloud tiers are far below 27 GB **[inference on current quotas]**, so recommend **Syncthing** (peer to peer, free, no size cap) for paks. On-demand placeholders (OneDrive Files On-Demand) download on read, slowly. Don't rely on `FileSystemWatcher` on cloud folders: poll on startup/refresh. Object GC is a manual "Clean up share" that keeps the last N revisions (`history/<rev>.manifest`) |
| **GitHub repo** | orders + manifest only | Repo holds `share.manifest` + `orders/`. Git gives history and diff for free; friends read it through the URL transport. v1 publish = "Export share files to folder" + you commit with git or GitHub Desktop. Later: publish through the API with a token | **Never paks**: GitHub's 100 MB file limit and repo size guidance, and redistributing Nexus mods publicly may break authors' permissions. Tokens need secure storage; today's Nexus key is plaintext (CLAUDE §7). Use DPAPI (`ProtectedData`) behind an `ISecretStore` so Linux can add libsecret later |
| **Gist** | orders + manifest | Same as repo, single file. Read through the raw URL | "Secret" gists are *unlisted*, not private: anyone with the URL can read them. Say so in the publish dialog |
| **URL to a manifest** (gist raw, GitHub raw, Dropbox `?dl=1`, any static host) | orders + pins (+ optional `bundleUrl` to a full zip on a cloud drive) | Subscription stores the URL. Fetch with the Splat-registered `HttpClient` (App.xaml.cs), `If-None-Match`/ETag, 5 MB cap, JSON only. **Do not use `WebHelper`**: it swallows every exception (CLAUDE §7), and silent failure looks like "no changes" | Read-only by nature. Paks come from `sources` links; Stage 9's downloader can later act on Nexus ids |
| **Hand-off** (Discord, email) | `.bg3share` | Export / import file | Manual, but zero setup. This is what to build first |

Subscriptions are stored in `Data/sync.json`:
`{ id, kind: folder|url, location, publisher, lastRevisionId, mode: follow|review }`.
On `RefreshAsync` completion, a background check raises an alert such as
"Pengu's 'Co-op Run' changed: +3 mods, 1 update, 2 moved. Review". It **never auto-writes
`modsettings.lsx`** and never auto-installs paks unless the user ticked "auto-install from this
folder".

### 8.3 Version pinning

- Pins = `(uuid, version64, sha256)` per order entry via `pins` → `mods[modKey]`.
- Pin modes per subscription: **exact** (default; co-op), **minimum** (`local >= pinned` is fine),
  **any**.
- A **"Co-op ready" check** in the review view: every pinned mod installed at the pinned version (and
  hash, if "strict"), plus a list of what to get, with links. A green tick means "we can play".
  Whether BG3 itself refuses mismatched versions in multiplayer is **[inference: verify in game]**;
  the check helps either way.
- Installing a friend's pinned version only works when the payload is available (bundle or shared
  folder). Otherwise show "you have 1.2, they have 1.3" with the source link.

### 8.4 Diff and merge of an incoming order against a local one

All of it lives in a pure Core class, `OrderDiff`/`OrderMerge`, so it can be unit-tested in a future
test project (master has none; the avalonia branch's `src/Tests/` is a precedent, ideas only).

- **Two-way diff** (theirs T, mine M, by entry id, dividers included):
  added = T∖M, removed = M∖T, common = T∩M; **moved** = common entries not in the LCS of T and M
  restricted to common; **version** = for common mods, the pin compared with the locally installed
  `version64` (and hash).
- **Merge actions:**
  - *Take theirs* (default for `follow` subscriptions): result = T.
  - *Take theirs, keep my extras*: each of my extra entries goes in after its nearest predecessor in M
    that also exists in T (anchor insertion), or at its divider (S6.3) if it has one.
  - *Three-way* (when `Data/sync/<id>/base-<revisionId>.json` from the last sync exists): apply
    their insertions, deletions and moves relative to base onto mine. A **conflict** arises only
    when both sides moved the same entry to different neighbours, or one deleted what the other
    moved. Conflicts are listed for the user to pick.
- **Output:** always a new or updated *saved* order (e.g. "Co-op Run (synced)"), through
  `CreateSnapshot` so Undo works. Then run the existing dependency and missing checks and show their
  results.
- **View:** side-by-side columns with +/−/↕/version badges. It reuses the flat-row list from Stage 6
  (no WPF grouping).

### 8.5 Privacy

- **Mod list and order names are shared by definition.** Mention in the dialog that the list may
  include mods people would rather not share; offer per-mod exclusion (already in the picker, §4.1
  step 5).
- **Profile name**: used in `<Profile>_Current.json` and the default archive name (MWVM:3561-3565).
  Profile names are often real names. Show the name and allow renaming before export.
- **Paths**: no `FilePath`; P1 non-GUID UUIDs are hashed. `createdBy` holds only the app version.
- **Zip timestamps** show when files were written. Minor; set entry times from the pak's
  `lastWriteUtc`, not "now".
- **Never** include `Data/settings.json` (Nexus key in plaintext, CLAUDE §7).
- **Public transports** (GitHub, gist): orders only, a visible "this will be public/unlisted"
  warning, and no paks (§8.2).
- **Integrity is not trust:** SHA-256 catches corruption and half-synced files, not malice. Paks can
  carry Script Extender Lua **[inference]**. Import only from people you trust. Say this once in the
  subscribe dialog.
